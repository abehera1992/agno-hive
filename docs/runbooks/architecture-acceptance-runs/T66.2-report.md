## 2. Root cause of scenario 7b

Scenario 7b (a genuine `def`+call structure from an unrelated service, e.g. shipping, reaches `COMPLETE` for a fully conceptual, unanchored task) is not a bug in the structural detector T66.1 built — it is a fundamental information gap. Investigated exhaustively before writing any code:

- **A genuinely correct answer and scenario 7b's false positive are structurally identical** in every respect this architecture can observe without comparing content. Both are: a single, untruncated, retained observation; containing a real `def`/`class` header; containing a real dotted-call/assignment reference to a different identifier. The *only* difference between them is what the identifiers mean and which service they belong to — information this architecture only has access to as free text (task prose, file paths, delegation objectives), and every phase in this series (T63 through T66.1) has consistently, deliberately declined to compare free text as a relevance signal, because doing so degrades into exactly the keyword/path heuristic repeatedly ruled out.
- **Confirmed directly, not assumed:** removing the unanchored "structural floor" entirely (so an obligation with no concrete anchor can never be marked supported) would correctly reject scenario 7b — but it would *also* reject the genuinely correct, equally-unanchored answer to the real, established T3 task, reintroducing T64's original false negative. This was the entire reason T65/T66 exist. Verified by running the removal mentally against scenario 1 (the positive control) using the same code path scenario 7b uses: both are unanchored, so both would be rejected identically.
- **The earliest authoritative point evidence *could* be bound to intent is the delegation** (`MemberControlState.objective`/`evidence_required`, set at `_start_member_objective`). Investigated whether linking `EvidenceRecord` back to its producing delegation (`delegation_key`) could close the gap. Two findings: (a) it cannot be wired soundly without a broader refactor — `_record_evidence_from_observation` is called from inside `_read_cache_tool_hook`, which is constructed and invoked without `team` (or the member control box) in scope at all, confirmed by reading `_make_read_cache_tool_hook`'s own signature and `_build_team`'s hook-wiring order directly; and (b) even if wired, it would not close the gap — a real, deliberate delegation to the wrong service (the Coordinator genuinely but mistakenly believing shipping-service was relevant) still produces a real, valid `delegation_key`. Not implemented, for both reasons.

## 3. Selected design and why it is sound

Given neither code change above is safe or sufficient, the smallest sound, additive change available is making the uncertainty **visible instead of silently collapsed**, directly implementing Section 4's required separation of relevance from support:

- `_relationship_support_claim` now records, in the `Claim`'s own `provenance` string, whether its structural connection was checked against a concrete anchor (`"...definition_plus_reference_anchored"`) or accepted on the structural floor alone with nothing to check against (`"...definition_plus_reference_unanchored"`).
- `_evaluate_requirement_coverage` reads this back and reports a new, still non-blocking coverage value, `"supported_unscoped"`, distinct from `"supported"`.
- `_completion_decision`'s `COMPLETE` path now returns an explicit, honest reason string whenever the only thing preventing `INSUFFICIENT_EVIDENCE` was an unscoped claim — naming the targets, naming the reason it wasn't blocked, and naming the architectural limitation — instead of the generic `"evidence ledger holds at least one observation"` every other `COMPLETE` outcome gets.

This is sound because it changes **no binary outcome** (every pre-existing `COMPLETE`/`INSUFFICIENT_EVIDENCE` decision is unchanged, confirmed in section 6) — it only adds a new, correctly-scoped disclosure dimension, reusing the exact `Claim`/provenance mechanism T66 and T66.1 already built rather than a parallel structure. It does not manufacture certainty where none exists (Section 3's own instruction): it names the uncertainty instead.

## 4. Relevance vs. relationship support — the distinction, concretely

- **B (support, resolved by T66.1):** does a single real observation contain a genuine definition and a genuine call/assignment reference to a different identifier? Answered deterministically, structurally, reused unchanged this phase.
- **A (relevance, NOT resolved by this phase):** does that observation actually concern the specific task's own scope? Answered only when a concrete anchor exists (an explicitly named entity or file path) — reusing the exact identity match `_evaluate_requirement_coverage`'s own `declared_exact` path already trusts. When no anchor exists, this question has **no answer available** under this architecture's own constraints, and this phase makes that fact visible (`"supported_unscoped"`) rather than pretending the question was answered.

## 5. Jev-style semantic relevance assessor — documented, not implemented

Per Section 5's explicit request, the full design a bounded semantic assessor would need, if a future phase decides to build one:

- **Exact question:** "Does this specific EvidenceRecord's content concern the same subsystem/service/functional area the user's task is asking about?" — a single, narrow relevance classification, never asked to judge correctness of the relationship itself (that remains B, the deterministic structural check, unchanged).
- **Minimal state and evidence it would receive:** the task's own original text (unmodified); the specific EvidenceRecord's `source_path` and `excerpt` (never the full file, never other unrelated evidence); nothing else — no conversation history, no other members' output, no prior assessments (to prevent it from being swayed by anything other than the one comparison it exists to make).
- **Fixed output categories:** exactly three — `relevant`, `irrelevant`, `abstain`. No free-text explanation is treated as authoritative; `abstain` is a first-class, expected output, not a failure.
- **Uncertainty and abstention policy:** `abstain` (or any response that doesn't cleanly map to one of the three categories) must be treated identically to "no assessment available" — i.e., the obligation stays `"unknown"`/`"supported_unscoped"` exactly as today. The assessor is never permitted to produce `"satisfied"` or `"missing"` directly; it may only gate whether a structurally-support ed claim is *also* counted as scope-verified.
- **Deterministic rules that consume its result:** the assessor's `relevant`/`irrelevant` output would feed into `_relationship_support_claim` as an *additional*, optional anchor source — a `relevant` verdict would let an otherwise-unanchored observation be treated as if an anchor existed (promoting `"supported_unscoped"` to `"supported"`); an `irrelevant` verdict would exclude that specific observation from `_relationship_support_claim`'s scan entirely (never promoted to `"missing"` — the absence of this one piece of evidence is not proof nothing else exists). The existing deterministic structural check (`_DEFINITION_RE`/`_REFERENCE_RE`) remains the sole authority for whether a *connection* exists; the assessor never bypasses it and never becomes a second completion gate.
- **Cost, latency, and failure implications:** one model call per unanchored, structurally-qualifying observation per completion-decision evaluation (bounded — `_relationship_support_claim` already stops at the first qualifying record, so this is at most one call, not one per ledger entry). A model/API failure must resolve to `abstain`, never to a default `relevant` (fail-closed, consistent with Section 3's "fail closed" requirement) — and must never retry indefinitely or block the run; a single bounded attempt with a hard timeout, falling through to the current, unchanged `"supported_unscoped"` behavior on any failure.
- **Adversarial evaluation required before enabling it:** at minimum, re-run this phase's own 14-scenario adversarial suite plus scenario 7b with the assessor live, confirming (a) it correctly abstains or says `irrelevant` for scenario 7b's own shipping-service excerpt against the seller-verification task, (b) it does not say `irrelevant` for any of the existing positive controls (1, 5c, 10a), and (c) a deliberately adversarial excerpt engineered to *look* relevant (e.g., containing the word "seller" in an unrelated comment) does not flip it to `relevant` — i.e., the assessor itself must be evaluated against the same false-positive discipline this entire phase series applies to deterministic checks, not assumed correct because it is a model.

This design is documented, not built, this phase, per the explicit instruction not to introduce a model dependency or new call "merely to complete this phase."

## 9. Remaining limitations

- **Scenario 7b's binary outcome is unchanged and remains open**, for the reasons in section 2: this is not a defect left unfixed by oversight, but a result confirmed to be underdetermined by every signal this architecture (and this entire phase series) permits itself to use. Closing it requires either the documented-but-not-built semantic assessor (section 5) or a relaxation of the keyword/model-dependency constraints every phase from T63 onward has deliberately upheld.
- **The new `"supported_unscoped"` disclosure is a transparency improvement, not a correctness one.** It does not reduce the actual false-positive rate; it makes the existing false-positive rate auditable. A future phase (or a human reviewing a live run) can now specifically search the journal/disclosure for `"supported_unscoped"`/`"no concrete anchor was available"` to find every completion decision that rests on this specific, named uncertainty — which did not exist as a searchable signal before this phase.
- **The delegation-lineage binding (`EvidenceRecord.delegation_key`) remains a genuinely valuable, not-yet-built provenance improvement**, independent of whether it would have closed 7b (it would not have, confirmed in section 2) — it is still the correct "minimum additional metadata" answer to Section 2's own request, and the smallest viable next step is the prerequisite architectural change it needs: threading `team` (or the member control box) into `_read_cache_tool_hook`'s construction and invocation, which `_build_team` does not do today.

## Verdict: **PARTIAL**

Grounded directly in the mission's own two relevant criteria. By the PARTIAL criterion ("the runtime is safer but still cannot establish task-scoped relevance reliably"): the runtime is demonstrably safer — the ambiguity that was previously silent is now a named, auditable, non-blocking disclosure, confirmed firing exactly where intended (scenarios 1 and 7b) and nowhere else (scenario 5c) — but task-scoped relevance is still not established reliably for the fully-unanchored case, confirmed and explained precisely in section 2. By the FAIL criterion ("unrelated evidence can still satisfy a mandatory obligation"): read literally, scenario 7b's binary outcome is technically still `COMPLETE`. This report does not minimize that: scenario 7b does not pass as a strict binary check, and that is stated plainly in sections 2 and 6 rather than disguised by the disclosure improvement. PARTIAL is used here because the disclosure change is a genuine, verified architectural improvement in exactly the direction Section 4 requires (separating relevance from support), not a cosmetic relabeling — but a reader who holds the binary outcome as the only criterion that matters would be equally justified calling this FAIL, and this report makes the evidence for that reading available rather than arguing it away.
