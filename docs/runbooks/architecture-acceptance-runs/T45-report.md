# T45 — Upstream Agno `member_run_id`/`register_member_run` Backport for Race-Safe Delegation Correlation

## 1. Executive verdict

| Dimension | Verdict |
|---|---|
| Investigation | **PASS** |
| Implementation | **PASS** |
| Isolated concurrency validation | **PASS** |
| Deployment | **PASS** (after a self-caught, self-fixed regression — see §7) |
| Live validation | **PARTIAL** |

T45 closes the pre-`RunStarted` correlation race T43/T44 identified and left open. Rather than vendoring upstream's full cancellation-propagation commit or attempting a major-version upgrade, this phase extracted the one reusable idea — **generate the member's own run identity before dispatch, before the race window even opens, and pass it in explicitly** — and implemented it as a small, defensive wrapper with zero changes to the installed Agno package. A deterministic, out-of-order concurrency harness (the mission's own mandatory gate) proves this is correct even under genuinely reversed completion order. Deployment included one real, observed production failure, caught and fixed within the same phase — disclosed here in full.

## 2. Verified Agno version and upstream target

Installed (ZGX and local): **2.5.17**, unchanged throughout this phase. Upstream target commit: **`1444c9bc3ea2bca322e377d9537d78499a6fb929`**, first released in **v2.6.10** (a 2.x minor release — correcting T44's own lower-confidence estimate of "requires 3.x," which was based on indirect web search; this phase's direct `git log -S` search against a full upstream clone settles it with commit-level precision).

## 3. Upstream provenance and what it actually does

Commit `1444c9bc3`, "feat: update agent, team and workflow cancel run persistance" (#5996), authored 2026-05-29. Its actual purpose is **run-cancellation propagation**, not delegation-result correlation: it generates `member_run_id = str(uuid4())` before dispatching a member, so that `cancel_run(member_run_id)` can later cancel that specific in-flight member run when the parent team's own run is cancelled — tracked via a new `agno.run.cancel` registry (`register_member_run`/`aregister_member_run`, `raise_if_cancelled`, `register_member_drain_task`) that does not exist in the installed 2.5.17.

**Only the identity-generation idea was reused — the cancellation registry was deliberately not vendored.** Reimplementing agno's own `_get_delegate_task_function` (~800 lines, calling two private, non-exported nested helpers) was evaluated and rejected as unbounded maintenance risk, consistent with T44's own conclusion. A caller-supplied `run_id` is already a real, documented parameter on `Agent.run()`/`Agent.arun()` (confirmed in T43/T44) — the only missing piece was a way to supply one without editing Agno's own closures.

## 4. Before/after identity-lifecycle

**Before (T41/T43/T44 end state)**: the member's own `run_id` was always freshly auto-generated by Agno (`run_id = run_id or str(uuid4())`), unknowable until observed via a `RunStarted` event — itself following two real awaits (`aregister_run`, `aread_or_create_session`) that could resolve out of dispatch order under concurrency.

**After (T45)**: `_duplicate_delegation_gate_hook` generates the member's own `run_id` synchronously, at dispatch time, before any await — before the race window even opens — and registers it into a new `team._pending_entry_by_expected_run_id` table. A small, defensive `Agent.arun` wrapper (installed lazily, on first dispatch) reads this value from a per-asyncio-Task contextvar and injects it into the real call, consuming it once. `_claim_pending_entry_for_run` now checks this table for an **exact match** before falling back to its existing oldest-unclaimed heuristic — when the match exists, correctness no longer depends on arrival order at all.

## 6. Compatibility analysis and rejected alternatives

| Option | Outcome |
|---|---|
| A. Minimal upstream-derived backport (chosen) | Implemented: reuse the id-generation idea only, via a small wrapper — no vendored agno code, no installed-package edits |
| Full vendor copy of `_get_delegate_task_function` | Rejected — ~800 lines, two private non-exported helpers, unbounded drift risk on every Agno upgrade |
| Full Agno 2.5.17→3.x (or even →2.6.10+) upgrade | Not pursued this phase — the wrapper approach achieves the same correctness without touching the dependency version at all, avoiding any upgrade-compatibility risk across this codebase's extensive Agno integration |
| Retain current behavior (T44's own prior conclusion) | Superseded — this phase found a safe path T44 had not yet identified |

**A real regression during implementation, caught and fixed before commit**: the first implementation attempt eagerly wrote the pending entry's own `run_id` key at dispatch time, which pre-empted T41's existing claim-at-`RunStarted` fallback and broke 3 of the 15 directly-relevant existing tests (which simulate externally-sourced `run_id` values unrelated to this codebase's own pre-generated id). Fixed by separating "pre-registered exact-match candidate" (`_pending_entry_by_expected_run_id`) from "actually-claimed `run_id`" (`entry["run_id"]`, written exactly once, at real claim time) — the final implementation passes all 15 tests unmodified.

## 7. Deployment — including a self-caught, self-fixed regression

**First deployment (commit `9affad9`) broke the very first live run.** The commit's own module-level `_install_member_run_id_patch()` call printed on success. `main.py` imports `swarm.team` at its own module top level (line 26), **before** `_run_worker_main()` redirects `sys.stdout → sys.stderr` (that function's own docstring: "stdout must carry ONLY the final JSON result line"). The install print therefore landed on the real, unredirected stdout pipe `api/server.py` captures and `json.loads()`s as a single value, producing: `[api] worker died (the worker produced unparseable output: Expecting value: line 1 column 2 (char 1))`.

Journal evidence confirmed the run's own correlation logic was unaffected — `outcome: ok`, both delegations correctly, distinctly resolved — the corruption was purely this print landing on the wrong stream.

**Fixed immediately (commit `6a9a413`)**: the install call moved from module level into `_ensure_member_run_id_patch_installed()`, called lazily from inside the dispatch-time hook — the same timing every other `[team] ...` print in this file already relies on safely. Verified directly: simulating `main.py`'s own exact top-level import produces zero stdout output, both locally and against the deployed ZGX source, before redeploying.

**Redeployed and re-verified**: the identical live scenario then completed cleanly — correct dual-count answer, zero errors, patch confirmed installed (now correctly on stderr), service continuously healthy (same PID/uptime, no further restarts needed).

## 8. Harness setup and proof of genuine overlap + reversed completion

A temporary, isolated script (scratchpad only, never a tracked test file) with two parts:

- **Part 1**: a real `agno.agent.Agent` instance (model call stubbed, never reached) exercises the real, installed `Agent.arun` through the T45 wrapper — proving injection, consume-once clearing, no inheritance by a later call, and no override of an explicit `run_id`.
- **Part 2 (the mandated scenario)**: two real `asyncio.Task`s (via `asyncio.gather`) dispatch delegations A and B to the same member through the real `_duplicate_delegation_gate_hook`. An `asyncio.Event` barrier — no `sleep()` — deterministically holds A until B has genuinely completed. Confirmed: both were simultaneously pending; dispatch order A,B; **completion order genuinely reversed, B,A**; distinct pre-generated identities; the expected-id table fully drained; each result correctly, distinctly associated with zero cross-contamination; no FIFO/queue-position assumption needed anywhere.
- **Part 3**: an externally-sourced (non-pre-registered) `run_id` still resolves correctly via the existing, unmodified fallback.

Re-run 3× locally (deterministic each time) and once directly against the deployed ZGX source (identical pass).

**Disclosed limitation**: this harness does not combine a real model call with the out-of-order scenario in one run (that would require live concurrent model calls, unsafe to induce deterministically). The bridge between "Part 1 proves the wrapper injects correctly" and "Part 2 proves correlation resolves correctly given a known id" rests on direct code reading (confirmed in T43/T44: an injected `run_id` becomes the real `RunContext.run_id`), not a single combined live-model harness run.

## 9. Per-invocation correlation assertions and cleanup

All pass (§8, Part 2): both in-flight simultaneously; reversed completion order; distinct identities; full table drain (no stale registrations); correct, non-cross-contaminated per-entry results; zero FIFO dependency.

## 12. Unresolved risks and recommended follow-up

1. The `Agent.arun`-only coverage boundary (§10) — revisit only if a sub-Team member is ever added to this deployment's topology.
2. Genuine concurrent dispatch remains **NOT_EXERCISED** live across 7 consecutive phases (T39–T45) — correctness under that condition rests on this phase's own isolated harness (Gate D, PASS), not on any observed production occurrence.
3. The wrapper's own defensive design (fails silently to T41's existing mechanism if `Agent.arun`'s signature changes incompatibly) should be re-verified after any future Agno upgrade — it is designed not to crash, but its own continued effectiveness is not self-evident without a check.
4. General lesson for this codebase: **any future module-level code in `swarm/team.py` must be audited against `main.py`'s own import-before-redirect ordering** — this phase's own regression is the second-hand proof that this ordering is easy to violate by accident.
