## 2. The central semantic question — answered precisely

For the conceptual-trace task ("Trace it from the API route to the database model."), `_completion_decision` reaches `COMPLETE` via its final fallthrough line (`return "COMPLETE", "evidence ledger holds at least one observation"`) whenever:

1. `member_chars` is truthy (some member produced output), **and**
2. the ledger is non-empty (`ledger_empty` is `False`) — this alone skips the "ledger empty + no tool called" check entirely, **and**
3. `_task_evidence_obligations` returns a non-empty obligation list (true for this task shape, since `_NAMED_TRACE_RE` always matches it), **and**
4. `_evaluate_requirement_coverage`'s `missing` list is empty — which it always is for this task, because T65's own fix makes every obligation here `resolved=False`, and `_evaluate_requirement_coverage` reports `resolved=False` obligations as `"unknown"` unconditionally, **never** `"missing"`.

The mechanism permitting `COMPLETE` is exactly steps 2+4 together: a non-empty ledger of **any** content bypasses the only check capable of blocking (`ledger_empty`), and the coverage check — correctly, per T65 — never produces a blocking `"missing"` for an unresolved target. Nothing in the current implementation asks whether the ledger's content has anything to do with the obligation's own target.

Distinguishing the five situations named in the mission:
- **Absence of evidence** — correctly blocks (`INSUFFICIENT_EVIDENCE`, via the separate, untouched ledger-empty+no-tool-called check).
- **Evidence that is relevant but incomplete** (e.g. only the route side) — reaches `COMPLETE`.
- **Evidence establishing both endpoints independently** — reaches `COMPLETE`.
- **Evidence establishing an actual relationship/trace between endpoints** — reaches `COMPLETE`, via the exact same code path as the previous case — **the implementation cannot tell these two apart**, confirmed empirically (section 3, Cases D vs. E).
- **A requirement that cannot be reliably decomposed** — correctly folds to `COMPLETE` with explicit `UNKNOWN` disclosure (unrelated to this gap; this is the intended, pre-existing behavior for shape 5, e.g. Case H).

**Confirmed, concretely: a non-empty evidence ledger, endpoint presence, and an `"unknown"` status are each currently treated as sufficient for `COMPLETE` once any evidence exists — none of them is proof that the requested task was actually addressed.**

## 3. Scratch-harness scenarios (A–H), against the real implementation

Run via `t65_1_scenarios.py`, calling the actual imported `_task_evidence_obligations`, `_evaluate_requirement_coverage`, and `_completion_decision` directly (not reimplementations). No repository tests added, modified, or run.

|---|---|---|---|---|---|
| A | Conceptual task, empty ledger, no tool calls | both unresolved | both `"unknown"` | **INSUFFICIENT_EVIDENCE** | `_completion_decision`'s ledger-empty + no-tool-called check (rule 1) — correct, untouched by T65 |
| B | Conceptual task, non-empty but **unrelated** evidence (shipping-label route/model) | both unresolved | both `"unknown"` | **COMPLETE** | fallthrough: `"evidence ledger holds at least one observation"` |

| E | Conceptual task, evidence excerpt explicitly shows the route calling into the model | both unresolved | both `"unknown"` | **COMPLETE** | same fallthrough — **identical result and identical code path to Case D**; the implementation does not distinguish an explicit relationship statement from no relationship evidence at all |

**Central question, answered empirically:** Case B is byte-for-byte identical in outcome, coverage dict, and decision reason to Cases C, D, and E. The implementation cannot currently distinguish "evidence exists but is about something else entirely" from "evidence explicitly demonstrates the requested relationship." Cases F/G/H confirm the gap is isolated to unresolved conceptual targets — explicit, resolvable targets (F/G) and genuinely non-decomposable tasks (H) behave correctly and are unaffected.

## 4. Whether this is a concrete completion-semantics defect

**Yes, confirmed as a concrete, evidenced defect**, distinct from (and a side effect of) T65's own fix: before T65, a conceptual-trace task with *any* evidence (relevant or not) returned `INSUFFICIENT_EVIDENCE`, because the literal-substring check on a conceptual phrase like "the api route" never matched anything — including, correctly if accidentally, Case B's unrelated evidence, but also incorrectly Cases C/D/E's relevant evidence (T64/T65's own confirmed false negative). T65 fixed the false negative on C/D/E by making unresolved targets non-blocking — but as a necessary logical consequence of that same change, Case B lost the only check that was ever rejecting it, and now reaches `COMPLETE` identically to C/D/E.

## 5. Why no code change was made this phase

Every path toward distinguishing Case B from Cases C/D/E was considered and rejected as out of this phase's own explicit scope:

- **A content-relevance check** (keyword match against the conceptual phrase's own words, e.g. "api"/"route"/"database"/"model") — explicitly forbidden ("No model-based classification, broad keyword heuristics").
- **A relationship/lineage check** (verifying that a specific delegation's own evidence was gathered *in service of* this specific obligation, or that one piece of evidence actually connects to another) — this is exactly the relationship-lineage extension the mission explicitly instructs not to begin this phase, and is the same gap T65's own report already named as open and deferred.
- **A magnitude/threshold heuristic** ("more evidence records implies more likely relevant") — would be a speculative, unprincipled proxy with no basis in the existing architecture, and was rejected on the same grounds T63/T64 already used to reject similar proxies.
- **A reason-string/disclosure-only change**, leaving the binary `COMPLETE`/`INSUFFICIENT_EVIDENCE` outcome unchanged — considered, but rejected as exactly the kind of change the mission explicitly warns against ("Do not disguise a semantic gap by changing only the status label or logging"): it would not change Case B's actual outcome, only how it is described, and presenting that as a "fix" would misrepresent what was actually corrected.

No design satisfying "preserve compatibility for existing concrete, verified requirements" (F/G, correctly unaffected) while also correctly separating B from C/D/E was found that does not require one of the three forbidden/deferred mechanisms above. Per the mission's own explicit fallback ("If no safe implementation fits this phase's scope, make no code change and report the precise blocker"), no implementation change was made.

## 6. Remaining limitations and deployment status

- **Limitation, confirmed and unresolved:** for any task whose obligations are entirely composed of unresolved (`resolved=False`) conceptual targets, `_completion_decision` cannot distinguish relevant from irrelevant evidence, or endpoint presence from a verified relationship, once the evidence ledger is non-empty. This is strictly narrower than — and does not reopen — T65's own fix: explicit, resolvable targets (file paths, named entities) remain correctly checked and correctly block on genuine absence (Cases F/G).
- **No regression introduced or found in T62 (whitespace detection), T63 (coordinator progress guard), or T64 (coverage logging)** — none of their code was inspected for change, none was touched, consistent with the mission's scope constraints. T64's own logging correctly continues to surface the `"unknown"` values that make this gap visible in the first place.
- **Deployment status: not applicable.** No code change was made; ZGX remains at `a33bb3c` (T65's deployed code), unchanged. No restart was performed.
- **Smallest real next step, not started this phase:** the relationship-lineage extension already proposed in T65's own report (section 10 there) — associating a delegation's own stated `evidence_required` with the specific evidence it produced, so a future completion check could ask "was evidence gathered *in service of* this specific unresolved target" rather than "does any evidence exist anywhere in the run." This remains the only identified path to closing the Case-B-vs-C/D/E gap without a forbidden relevance mechanism, and is explicitly not begun here per this phase's own instruction.

## Verdict

Confirmed defect: **unresolved conceptual requirements can reach `COMPLETE` with evidence that does not establish, or is entirely unrelated to, the requested task — not merely with evidence that is "incomplete."** No implementation change was made this phase; the defect is reported, not disguised, and not fixed, pending the relationship-lineage work explicitly out of scope here.
