## 3. Original false-positive path and the correction

T66's `_relationship_support_claim(team)` accepted any single, untruncated, retained observation containing 2+ distinct code-identifier-shaped tokens as proof of a relationship, and one accepted claim marked **every** unresolved target in the current obligation set `"supported"`. T66's own report explicitly named both as acknowledged weaknesses: the signal "does not establish the semantic relationship required by a task," and "one accepted claim can classify every unresolved target in an obligation set as supported."

**Correction, two parts:**
- **Structural tightening:** `_relationship_support_claim(team, obligations)` now requires BOTH a real definition header (`_DEFINITION_RE`: `def foo(` or `class Foo`) AND a genuine call/assignment reference to a **different** identifier (`_REFERENCE_RE`: a dotted method call `X.method(`, or an assignment whose right-hand side is a call `x = X(`) within the same observation. A comment naming two sibling classes, an import statement, or two bare declarations with nothing calling into either satisfy at most one of the two patterns, never both with differing identifiers.
- **Obligation-specific scoping:** when the current obligation set contains at least one *resolved* (concrete) target, the reference side of the connection must normalize-match one of those anchors (reusing `_normalize_delegation_target`, the exact identity check `_evaluate_requirement_coverage`'s own `declared_exact` path already trusts). A structurally real connection to the wrong entity is now correctly rejected when an anchor exists to check against.

**Prerequisite fix:** `_resolve_trace_target`'s tier 2 (embedded-entity detection) called `_EVIDENCE_ENTITY_RE` directly, which requires a literal leading `"the "` — but `_NAMED_TRACE_RE`'s own second capture group never has one (its enclosing non-capturing group already consumes it). This meant tier 2 never actually fired for a `_NAMED_TRACE_RE` second endpoint, confirmed and flagged as an open limitation in T66's own report. Fixed via a new `_EMBEDDED_ENTITY_IN_SPAN_RE` (same shape, no leading-`"the"` requirement), which is a direct prerequisite for anchor-scoping to engage at all on task phrasings that name a concrete entity on either side of a trace.

## 4. Is support now obligation-specific?

Yes, within the architecture's existing limits. Confirmed via a hand-built, mixed obligation list (one resolved entity target, one unresolved relationship target) passed directly to the real `_evaluate_requirement_coverage`: the resolved target's `"satisfied"/"missing"` status is computed entirely independently of the relationship mechanism, and a validated relationship claim for the unresolved target has no effect on the resolved one or vice versa (section 5, scenario 6). When a concrete anchor is identifiable, the relationship signal is additionally scoped to that anchor — not "any real connection anywhere," but "a real connection to the specific named entity" (scenarios 5b/5c, 7a).

The current `_task_evidence_obligations` architecture can only ever produce **one** relationship-pair per task (from a single `_NAMED_TRACE_RE.search()` call) — it cannot represent two independent, separately-trackable relationship obligations in one task. This is an existing architectural boundary, not something this phase altered or could safely extend without the broader call-graph work explicitly out of scope; scenario 6 exercises the closest faithful analog (a mixed resolved+unresolved set) rather than two genuine relationship pairs, since the latter is not constructible via the real extraction function today.

## 9. Remaining semantic limitations

- **Unanchored, cross-service false positive (scenario 7b), honestly unresolved.** When a task is purely conceptual (neither endpoint resolves to a concrete entity — the established T3 phrasing's own shape) and evidence from a genuinely unrelated part of the codebase happens to contain a real `def`+call structure, this phase's structural-only floor cannot reject it. Closing this would require either a keyword/path-relevance heuristic (explicitly forbidden by this and every prior phase in this series) or a model-based semantic judge (explicitly forbidden this phase). Documented here rather than hidden, per this phase's own instruction to "document the limitation rather than manufacturing certainty."
- **No call-graph correctness is verified.** The structural signal proves "a real definition exists, and a real call/assignment to a different, real identifier exists in the same observation" — never that the call is semantically correct, reaches the right line, or that the "model" side is actually a persistence model rather than, say, a logger. This was already acknowledged in T66's report and remains true; T66.1 narrows the false-positive surface without claiming full semantic verification.
- **The current obligation-extraction architecture still represents only one relationship-pair per task.** Scenario 6's "multiple obligations" requirement was tested via the closest faithful analog (a mixed resolved+unresolved set) rather than two genuine, independently-tracked relationship pairs, since the latter cannot be produced by the real `_task_evidence_obligations` today. Extending it to support multiple relationship pairs was not attempted, consistent with "do not expand into a general call-graph engine."
