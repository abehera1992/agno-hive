# AGNOHive Skills Architecture — Progressive Disclosure for Bootstrap Context

**Date:** 2026-08-01
**Status:** Approved
**Scope:** AGNOHive (`agno-hive`) — `swarm/team.py`, `swarm/agents.py`, `hive-mcp/`, plus per-project `skills/` directories (e.g. `EkamApp/skills/`)

---

## Problem

Every AGNOHive run pays a large, fixed context cost before any agent reads a single file relevant to the actual task. Measured 2026-08-01 against the current `qwen3-30b-hive-v2` production swarm:

- `_COORDINATOR_INSTRUCTIONS` in `swarm/team.py` — 17,107 chars (~4,300 tokens), sent to the coordinator on every run regardless of task. Covers tool restrictions, honesty/anti-fabrication rules, the count-marker mechanism, conversational-turn classification, scan-first rules, Notion grounding (5 sub-rules), external-docs-vs-code rules, file-write-review protocol, output-format guard.
- hive-mcp's `_instructions` in `hive-mcp/main.py` — 7,325 chars (~1,800 tokens), sent as the MCP server's `instructions` field on every connection. Same shape: file-editing rules, Notion grounding rules (again), counting rules (again), DB-backed-facts rules — present whether or not the task needs them.
- `hive.md` (auto-generated project snapshot) — 23,944 chars (~6,000 tokens) — the coordinator instructions call this "your first action for any non-trivial task."
- `patterns/ekam-code-generation-guards.md` — 41,589 chars (~10,400 tokens) — pulled in for "any code-writing task."

Stacked, an ordinary code-writing task carries **~22,500 tokens of fixed overhead** before the coordinator reads anything specific to the question asked. This matches a failure mode already independently diagnosed in `hive-mcp/main.py:153` (`_conventions_block()`'s docstring): a "write a component following this project's conventions" task spent its whole run *hunting* for the rules already buried in this same bloat, producing a pass, a failure, and a 600s non-termination across three otherwise-identical runs. The `_conventions_block()` fix (inlining conventions into the instructions) treated a symptom — it added yet more always-on text rather than making the relevant text findable only when relevant.

An agent with N capabilities currently pays for all N on every task instead of routing to the one it needs.

---

## Goals

- Replace always-on instruction blocks with a small, always-on **L1 catalog** (name + one-line description per skill) plus **on-demand full-text loading** via a new `load_skill(name)` tool.
- Preserve the existing hive-mcp / project split: hive-mcp ships generic protocol skills; each connected project supplies its own project-specific skills. Neither the model nor the mechanism needs to know which catalog a skill came from.
- Scope each agent role (Coordinator, ContextRouter, Researcher, Planner, Coder, Executor, Reviewer) to the subset of skills relevant to its job, mirroring the existing per-agent tool-scoping in `agents.py`.
- Fold `hive.md` and `patterns/*.md` into the same mechanism, closing the two largest concrete bloat sources found above.
- Validate the change via the existing 40-case eval harness (`training/eval/agent_harness.py`, best/majority/strict methodology) before cutover — no new enforcement mechanism, no change to the on-demand tool-call design.

## Non-Goals

- Changing the 6-agent pipeline, `coordinate`/`collaborate` modes, the `read_only` flag, or `_MUTATING_TOOLS` — orthogonal, untouched.
- Changing session-chain handoff summaries (`_extract_handoff_summary`) — already progressive-disclosure-shaped, kept as-is.
- Changing `verify_claims` grep-based fact-checking — unrelated layer, kept as-is.
- Adding a deterministic pre-router or any enforcement mechanism to guarantee `load_skill()` gets called. This was considered and explicitly declined in favor of the on-demand design faithful to the reference architecture (Claude Skills / the "Anatomy of Agent Skills" progressive-disclosure model); see Risks below for how this gets measured instead of enforced.
- Migrating `DOCS.md` (agno-hive's own 108KB self-documentation) — out of scope for this pass; flagged as a candidate for a future skill if it turns out to matter.

## Architecture

### File layout

```
agno-hive/hive-mcp/skills/                      # generic, ships with hive-mcp
  notion-grounding/SKILL.md
  db-facts/SKILL.md
  counting-marker/SKILL.md
  file-write-review/SKILL.md
  verification-discipline/SKILL.md

EkamApp/skills/                                 # project-specific, per connected project
  project-overview/SKILL.md        # replaces hive.md's role; generated by `hive --scan`
  code-generation-guards/SKILL.md  # was patterns/ekam-code-generation-guards.md
  frontend-conventions/SKILL.md    # was patterns/ekam-frontend.md
  migrations/SKILL.md
```

Each `SKILL.md` is YAML frontmatter (`name`, `description`, `roles: [...]`) plus a body. `roles` values are the exact agent `name` strings already used in `swarm/agents.py` (`Coordinator`, `ContextRouter`, `Researcher`, `Planner`, `Coder`, `Executor`, `Reviewer`) — no new naming scheme. The body is the existing instruction text, moved verbatim — this is a repackaging of already-validated rules, not a rewrite of what they say.

### Catalog assembly

hive-mcp already knows which project it is mounted against (the existing `EkamApp/hive-mcp.env` pattern for exclusions/lint config). At startup it globs its own `skills/` directory plus the connected project's `<project_root>/skills/` directory and merges both into one **L1 catalog**: `{name, description, roles}` per skill. This is the only thing present in every run's context unconditionally — roughly 100 tokens per skill, flat regardless of how many skills exist. The model never sees which catalog (hive-mcp vs project) a given skill came from; only `roles` affects what it sees.

### Role scoping

Each agent spec in `swarm/agents.py` gains a `skill_roles` field. When a run assembles an agent's system prompt, the L1 catalog is filtered to entries whose `roles` list includes that agent's role — e.g. Executor never sees `notion-grounding`; Coder always sees `code-generation-guards` and `file-write-review` in its L1 list. The coordinator sees the union of all roles (it can delegate anything). This mirrors the existing per-agent tool-scoping already done in `make_agent_from_spec`.

### `load_skill(name)` — on-demand full text

A new hive-mcp tool, present in every agent's toolset alongside `get_file_content`. Returns a matched skill's full body text. This directly replaces:

- `_COORDINATOR_INSTRUCTIONS` in `team.py` — the 17K-char always-on blob is deleted; what remains is the L1 catalog's one-line descriptions. Full text for Notion grounding, counting-marker mechanics, file-write-review protocol, etc. moves behind `load_skill(...)`.
- hive-mcp's `_instructions` in `main.py` — same treatment, same reasoning.
- `_conventions_block()`'s eager inlining is removed. The underlying "hunting for conventions" problem is instead solved by giving the `code-generation-guards` skill a description precise enough to be a one-hop lookup ("call this before writing or editing any code in this project — required conventions and anti-patterns") rather than requiring the model to find the rules buried in loaded context.

### `hive.md` and `patterns/*.md`

`hive --scan` continues to generate the same content, but writes it to `EkamApp/skills/project-overview/SKILL.md` instead of `hive.md`. Each `patterns/*.md` file gains a `description` frontmatter line and moves under `EkamApp/skills/`. The current instruction "call `get_file_content('hive.md')` as your first action for any non-trivial task" is deleted outright — nothing replaces it except the L1 catalog entry:

> `project-overview` — "Directory tree + module summaries. Load before answering structure/overview questions or when you need codebase orientation."

## Validation

The risk accepted by choosing on-demand loading over a deterministic pre-router: a model can simply not call `load_skill()` when it should have. This session already has direct evidence that instruction text alone doesn't reliably constrain behavior (the `read_only` mechanism exists specifically because an explicit "do NOT call write_file" instruction was ignored once). The mitigation here is measurement, not a second enforcement layer — adding one would reintroduce the hybrid design that was explicitly considered and declined.

Before cutover:
1. Extend `training/eval/agent_cases.json` with cases that specifically require a skill's content to answer correctly — a Notion-grounding question, a code-write that must follow `code-generation-guards` — and score `FAIL` when the answer shows the known symptom (fabricated Notion id, wrong convention used) even if superficially plausible. `verify_claims` already supports this style of grounding check.
2. Run the full 40-case suite through the existing best/majority/strict aggregation (`training/eval/aggregate_runs.py`) on both the current instruction-blob build and the new skills build.
3. Cut over only if the skills build is not worse than the current baseline on the extended suite. If specific skills prove unreliable to self-select (chronic non-calls on cases that need them), promote just those skills into the pre-routed set — the hybrid approach remains available as a targeted fallback for skills that measure badly, rather than a blanket default.

---

## Open follow-ups (not blocking this design)

- `DOCS.md` (agno-hive's own self-documentation, 108KB) is unconverted. If ContextRouter/Researcher tasks that introspect agno-hive itself show the same bloat symptoms, it becomes a future skill.
- No skill-usage telemetry is specified here beyond what `_traced()` tool-call logging already captures (`load_skill` calls will show up in the existing trace the same way any other tool call does).
